## 1. The 833ms is proven, by elimination

Your reported `auth_method: local_jwks` narrows this to exactly one line of code.

`authMethod` is initialised to `'local_jwks'` at line 544 and is only ever reassigned **on failure**:

```ts
let authMethod = 'local_jwks';                                    // 544
let localClaims = jwt ? await verifyJwtWithJwks(jwt, supabaseUrl) : null;  // 545
if (!localClaims) { authMethod = 'local_hs256'; ... }             // 546
```

So `local_jwks` in your metrics means `verifyJwtWithJwks` **succeeded** — it found the `kid`, imported the key, and verified the signature. `getClaims` was never called. `getUser` was never called. The entire 833ms is inside `verifyJwtWithJwks`.

That function does exactly four things:

| Step | Cost |
| --- | --- |
| Parse header, extract `alg` / `kid` | microseconds |
| `getJwks(supabaseUrl)` — line 288 | **the 833ms** |
| `crypto.subtle.importKey` — line 295 | ~1ms |
| `crypto.subtle.verify` — line 304 | ~1ms |

So it is the `fetch()` on line 265, which means `jwksCache` was **null** when the request arrived.

**Your cache code is correct.** Lines 261–278 do module scope, a 10-minute TTL, and in-flight deduplication. There is no `kid` mismatch (the key was found, or you would have seen `local_hs256`). There is no scope bug. There is nothing to fix in that function.

**The cache was empty because the isolate was new.** Your hypothesis #1 was right and #2 and #3 were wrong. Confirmed by elimination from the source, so you can skip the `boot_id` experiment if you want — though see section 3, because you still need it for a different reason.

## 2. Why it is 833ms and not 50ms — this changes the fix

A JWKS fetch over an established connection is 30–80ms. You are paying 833ms because **this is the isolate's first outbound HTTPS request**: DNS resolution, TCP handshake, and TLS negotiation to the Supabase auth host, all cold, before a single byte of JWKS is transferred.

You are not measuring a slow endpoint. You are measuring connection establishment.

This matters because it rules out the fix you might reach for first. Better caching cannot help a cache that is structurally empty on every new isolate, and a longer TTL cannot help either. **The only fix that works is not making the request at all.**

## 3. The second cold-connection cost, which nobody has been measuring

This is the finding I would not have made without the source, and it is worth roughly as much as the auth fix.

The JWKS fetch goes to `{SUPABASE_URL}/auth/v1/...`. The model call goes to `openrouter.ai` (line 22). **Different host — so it pays its own DNS, TCP, and TLS handshake, cold, every time.**

And your warm-up cannot help, because it returns at line 588:

```ts
if (body?.warm_up === true) {           // 586
  timing.total_ms = ...;
  return json(200, { status: 200, warm: true, timing });   // 588
}
```

`extractBalanced` is never called on a warm-up, so the OpenRouter connection is never established. Every real scan pays cold TLS to OpenRouter, and that cost is **hidden inside your 1331ms `model_ms` bucket**, which you have no sub-timings for.

Expect 200–400ms of your model time to be connection setup rather than inference. Two consequences:

- Add a `provider_ttfb_ms` / `generation_ms` split so you can see it.
- Have the warm-up path make a trivial OpenRouter request before returning, so the connection exists. This is a bigger win than anything else on your V3.1 list except the auth fix.

Note the honest caveat: this only helps when the warm-up and the scan share an isolate — which is exactly the thing that is currently failing. Which is why the keep-warm schedule matters more than you credited it. Keep `boot_id` in your metrics for this reason, even though you no longer need it to diagnose auth.

## 4. Bugs found in the source, ranked

### 4.1 `getJwks(url, true)` has no cooldown — latent request storm
**Line 291.** On unknown `kid`, you force-refetch with `force = true`, which bypasses the cache unconditionally:

```ts
let jwk = keys.find((key) => key.kid === kid);
if (!jwk) {
  keys = await getJwks(supabaseUrl, true);   // no cooldown, no negative cache
  ...
}
```

During a key rotation, or if any client ever presents a token signed by a key absent from your JWKS, **every single request performs two sequential uncached fetches** to your auth endpoint — with zero backoff. At 400–800ms each that is a 1.6s auth cost, and it is a self-inflicted request storm against your own auth server, at exactly the moment it is already under stress.

Add a cooldown (30s minimum between forced refetches) and a short negative cache for unknown `kid`s.

### 4.2 `verifyJwtWithJwks` swallows every error identically
**Lines 315–317.** `catch { return null }` means a forged signature, a network failure, a malformed key, and an expired token are indistinguishable. All four fall through to `local_hs256` → `claims` → `getUser`.

Not exploitable — the later tiers reject bad tokens too — but two real costs:

- A bad or forged token costs you a full `getClaims` round trip. That is a cheap amplification vector on a paid endpoint.
- You cannot tell an attack from an outage in your metrics.

Split the failure modes: signature or `exp` failure should **fail closed immediately**; only a network or unknown-`kid` failure should fall back.

### 4.3 `SUPABASE_JWT_SECRET` is not set anywhere, so tier 2 is dead code
`verifyJwtLocally` (line 234) returns `null` at line 236 whenever the secret is absent, and I found no `SUPABASE_JWT_SECRET` or `JWT_SECRET` in `.env`, `.env.staging`, `.env.production`, or `.env.example`.

So your fallback chain is really `local_jwks` → *(nothing)* → `getClaims` → `getUser`. That is fine once auth is fast, but you should know that the middle tier you think you have does not exist. Either configure it or delete it — dead security code is worse than absent security code, because it reads as a safety net that is not there.

### 4.4 The `getUser` fallback is duplicated
**Lines 551–567 and 568–577** are near-identical `if (!isUuid(userId))` blocks, both terminating in `auth.getUser()`. In the happy path the second is skipped. On a failure path you can call `getUser()` twice sequentially, doubling the latency of your worst case. Collapse them.

### 4.5 `normalize_ms` is hardcoded, not measured
**Line 447:** `timing.normalize_ms = 0;`

Your report of "normalize/validation 0.000s" is a literal, not a measurement. `normalizeExtraction` does regex date parsing and array mapping — it is probably genuinely fast, but you have not verified it, and you currently believe you have.

### 4.6 422 is reachable *and* in your retryable set
**Line 630:** `rejectEmptyExtraction` returns 422. Per your architecture doc, 422 is a retryable status. So an empty extraction triggers three attempts of a request that will fail identically each time, burning ~11s of wall clock to arrive at the same answer. Remove 422 from the retryable set, as flagged in the earlier review — now confirmed reachable rather than theoretical.

### 4.7 Hot-path DB read is one client bug away
**Lines 614–626.** If `default_currency` is missing from the body you run a `profiles` select on the hot path. `profile_ms` is 0 today because the client always sends it. But this is a latent round trip sitting exactly where your 833ms used to be. Default to `'USD'` and reconcile asynchronously instead of blocking.

### 4.8 `provider: { require_parameters: true }` may be narrowing your routing
**Line 350.** Combined with `reasoning` and `strict: true` json_schema, this restricts OpenRouter to upstreams supporting every parameter you pass. That can route you to fewer or slower providers, or add routing latency. Worth an A/B with it off, measured against `provider_ttfb_ms` once you have that metric.

### 4.9 `config.toml` has no `[functions]` block
There is no `verify_jwt` setting anywhere in the repo, so deployed functions are on the platform default (`true`). To disable it you need:

```toml
[functions.extract-balanced]
verify_jwt = false
```

But as established last round, this is capped by your measured 128ms gap. Expect 30–70ms, and read the caveats before doing it — you take on the rate limiting the gateway was providing, on an endpoint that spends money.

## 6. The fix

Replace the fetch with an env-provided JWKS, imported once at module load.

```ts
// ── module scope: runs once per isolate, zero network ──
type Jwk = JsonWebKey & { kid?: string; alg?: string };

const keyCache = new Map<string, CryptoKey>();
let jwksCache: { keys: Jwk[]; fetchedAt: number } | null = null;
let lastForcedFetchAt = 0;
const FORCE_COOLDOWN_MS = 30_000;

const algParams = (alg: string) =>
  alg === 'ES256'
    ? { import: { name: 'ECDSA', namedCurve: 'P-256' }, verify: { name: 'ECDSA', hash: 'SHA-256' } }
    : { import: { name: 'RSASSA-PKCS1-v1_5', hash: 'SHA-256' }, verify: { name: 'RSASSA-PKCS1-v1_5' } };

// Seed from env at boot. No await, no fetch.
const seeded = Deno.env.get('SUPABASE_JWT_PUBLIC_JWKS');
if (seeded) {
  try {
    const parsed = JSON.parse(seeded);
    const keys: Jwk[] = Array.isArray(parsed?.keys) ? parsed.keys : [];
    jwksCache = { keys, fetchedAt: Date.now() };
    await Promise.all(
      keys.map(async (jwk) => {
        if (!jwk.kid || !jwk.alg) return;
        keyCache.set(jwk.kid, await crypto.subtle.importKey(
          'jwk', jwk, algParams(jwk.alg).import, false, ['verify'],
        ));
      }),
    );
  } catch (error) {
    console.error('[extract-balanced] SUPABASE_JWT_PUBLIC_JWKS is malformed', error);
  }
}
```

Then the verification path resolves from `keyCache` first and only touches the network for a genuinely unknown `kid`, behind the cooldown:

```ts
type AuthOutcome =
  | { ok: true; claims: Record<string, unknown>; source: 'env' | 'fetched'; fetchMs: number }
  | { ok: false; reason: 'malformed' | 'bad_signature' | 'expired' | 'unknown_kid' | 'fetch_failed' };

async function verifyJwtWithJwks(jwt: string, supabaseUrl: string): Promise<AuthOutcome> {
  const parts = jwt.split('.');
  if (parts.length !== 3) return { ok: false, reason: 'malformed' };

  let header: { alg?: string; kid?: string };
  try { header = base64UrlToJson(parts[0]); }
  catch { return { ok: false, reason: 'malformed' }; }

  const alg = String(header?.alg ?? '');
  const kid = String(header?.kid ?? '');
  if (!kid || (alg !== 'ES256' && alg !== 'RS256')) return { ok: false, reason: 'malformed' };

  let key = keyCache.get(kid);
  let fetchMs = 0;
  let source: 'env' | 'fetched' = 'env';

  if (!key) {
    // Unknown kid — rotation. One fetch, behind a cooldown.
    if (Date.now() - lastForcedFetchAt < FORCE_COOLDOWN_MS) {
      return { ok: false, reason: 'unknown_kid' };
    }
    lastForcedFetchAt = Date.now();
    const t0 = performance.now();
    try {
      const res = await fetch(`${supabaseUrl}/auth/v1/.well-known/jwks.json`);
      if (!res.ok) throw new Error(`JWKS fetch failed with ${res.status}`);
      const body = await res.json();
      const keys: Jwk[] = Array.isArray(body?.keys) ? body.keys : [];
      jwksCache = { keys, fetchedAt: Date.now() };
      for (const jwk of keys) {
        if (!jwk.kid || !jwk.alg) continue;
        keyCache.set(jwk.kid, await crypto.subtle.importKey(
          'jwk', jwk, algParams(jwk.alg).import, false, ['verify'],
        ));
      }
    } catch {
      return { ok: false, reason: 'fetch_failed' };
    }
    fetchMs = Math.round(performance.now() - t0);
    source = 'fetched';
    key = keyCache.get(kid);
    if (!key) return { ok: false, reason: 'unknown_kid' };
  }

  const verified = await crypto.subtle.verify(
    algParams(alg).verify, key, base64UrlDecode(parts[2]),
    new TextEncoder().encode(`${parts[0]}.${parts[1]}`),
  );
  // Fail CLOSED on a bad signature. Never fall through to getClaims here.
  if (!verified) return { ok: false, reason: 'bad_signature' };

  let claims: Record<string, unknown>;
  try { claims = base64UrlToJson(parts[1]); }
  catch { return { ok: false, reason: 'malformed' }; }

  const exp = Number(claims?.exp ?? 0);
  if (Number.isFinite(exp) && exp > 0 && exp * 1000 < Date.now()) {
    return { ok: false, reason: 'expired' };
  }
  return { ok: true, claims, source, fetchMs };
}
```

Caller changes:

```ts
const outcome = jwt ? await verifyJwtWithJwks(jwt, supabaseUrl) : { ok: false, reason: 'malformed' };
timing.jwks_source   = outcome.ok ? outcome.source : null;
timing.jwks_fetch_ms = outcome.ok ? outcome.fetchMs : 0;
timing.auth_reason   = outcome.ok ? null : outcome.reason;

// Fail closed — do NOT fall back for these.
if (!outcome.ok && (outcome.reason === 'bad_signature' || outcome.reason === 'expired')) {
  timing.auth_ms = Math.round(performance.now() - authStartedAt);
  timing.auth_method = 'rejected';
  return json(401, { code: 'VALIDATION_FAILED', message: 'Authentication required', timing });
}
```

Populate the secret from your project's JWKS:

```bash
curl -s "$SUPABASE_URL/auth/v1/.well-known/jwks.json" > jwks.json
# Confirm it contains BOTH the active and standby keys before setting.
supabase secrets set SUPABASE_JWT_PUBLIC_JWKS="$(cat jwks.json | jq -c .)"
```

Include the standby key so a planned rotation never hits the fetch path at all.

**Regression guard:** assert `timing.jwks_source === 'env'` on the happy path. A field that should always have one value is far easier to alarm on than a latency percentile.

## 8. Revised order

1. **Inline `SUPABASE_JWT_PUBLIC_JWKS`** with the module-scope import above. 833ms → ~3ms. This is the whole auth problem, and it is one env var plus one function.
2. **Add the cooldown and negative cache** to the unknown-`kid` path (4.1). Ship with #1 — it is the same function and it prevents a rotation from becoming an incident.
3. **Fail closed on bad signature / expiry** (4.2). Same function again. Do all three as one PR.
4. **Add `jwks_source`, `jwks_fetch_ms`, `provider_ttfb_ms`, `generation_ms`, and `boot_id`.** Cheap, and #6 depends on being able to see the result.
5. **Warm the OpenRouter connection in the warm-up path** (section 3) + keep-warm schedule every 30–60s.
6. **Split header / line-items calls.** `line_items` is `required` under `strict: true`, so this means a second schema — mechanically simple, and it is the only remaining item that creates margin.
7. Cleanups: 4.3 (delete or configure the dead HS256 tier), 4.4, 4.5, 4.6, 4.7.
8. `verify_jwt = false` **last**, with the rate limit in place, once your own verification is fast and hardened.

Steps 1–3 are one PR and remove the problem you started with.
