Supplements `docs/B4-handover-2026-07-31.md`. That document still describes the
B4 architecture correctly. This one covers a session spent on two things: the
offline cold-start failure it listed as open item 4.1, and a chain of sync
defects found while trying to verify the fix for it.

Branch: `feat/b4-extraction-fast-path`
Staging project: `receiptflow-staging` (`wfboznibkhsfxteejxco`)

Two commits:

- `1efd921` — carry the user's edits to the server, and stop losing rows mid-sync

Both edge functions (`receipt-confirm`, `extract-balanced`) **are deployed to
staging**. Everything else is committed but not released.

## 1. The app can now cold-start without a network (4.1, closed)

**The problem.** Start-up ran a single network transaction that had to succeed
before the session was ever applied, so launching without connectivity threw
away a perfectly valid stored session and dropped the user on the sign-in
screen. The offline capture queue built in B3 was unreachable in exactly the
situation it exists for.

**What changed.** Auth state is now three-valued — restoring, authenticated,
signed out — and restored from local storage first. Reference data is
revalidated in the background, where failing changes nothing the user can see.
`signed_out` is reachable only from an empty token store or an explicit
sign-out, never from a failed request.

The app now keeps its own record of who is signed in (`auth_cache`), separate
from the tokens. This matters because an access token older than an hour cannot
be refreshed offline: Supabase answers "no session" while deliberately leaving
the tokens on disk, and without a local record of the identity the app cannot
tell that apart from having no account. Routing switched from `session` to a
new `authenticated` flag, so a token that cannot be refreshed offline no longer
reads as signed out.

Three things were fixed in passing, all the same theme:

- Supabase's auto-refresh was never wired to `AppState`. React Native has no
  page lifecycle for it to hang on, so the token was only ever refreshed lazily
  at the moment of use — which is how it got old enough to be unrefreshable.
- A token refresh no longer flashes a full-screen spinner every 50 minutes.
- Signing out now clears locally even if the server call fails.

**Verified** on the simulator: an offline cold start reaches the camera with
the cached profile and categories. The snapshot was confirmed present in the
device database.

**Not covered:** the branch where identity comes from the snapshot alone. In
the test the access token was still valid, so it never exercised the
expired-token path. To hit it, leave the app closed for over an hour, then
launch offline.

## 2. The user's edits never reached the database

**The problem.** Confirming a receipt sent the corrected fields to the server
and the endpoint read nothing but the receipt id. Every edit — merchant, date,
total, category, notes — lived only on the device, while the database kept the
model's original reading. Nothing surfaced this because the app never reads
receipts back from the server.

This was found while planning hydrate-on-fresh-install, and it is why that work
stopped. Hydrating from a server that holds the model's guesses would silently
revert every correction a user had made — worse than an empty list, because
wrong numbers read as correct.

**What changed.** Confirmation now writes merchant, date, total, currency,
category and notes. It is written as "save these values", safe to call more
than once, so wiring editing from the Search screen later reuses it rather than
needing a second endpoint.

Resolving a category name to an id — and refusing any category the account has
not selected — moved into `functions/_shared/categories.ts` and is used by both
extraction and confirmation. Writing that rule a second time inside confirm is
exactly how Balanced drifted from Precise. The per-instance cache and the
timing instrumentation moved with it, so the 4.4 latency investigation is
unaffected.

**Line items are deliberately not written.** The model captures name, quantity
and amount, but that structure is flattened to plain text before it reaches the
device, so the phone cannot push back what it never received. Writing the
strings would overwrite real quantities with placeholders. See §5.

## 3. Rows that nothing ever re-drove

Three separate states could leave a receipt sitting "saved" on the phone
forever while the server never heard about it. All are fixed, and all were
invisible: no error, no retry, and the receipt looked fine in the app.

1. **`sync_failed_final`.** After five failed attempts a confirmed receipt was
   marked terminally failed — and the work list never selects that state, so
   nothing retried it, ever.
2. **`syncing` / `uploading`.** Both queues mark a row in-flight *before* the
   network call, and neither work list selects those states. A request that did
   not survive the process — app backgrounded as the receipt flies into the
   folder, request hung, process killed — stranded the row permanently. Both
   are now reclaimed after a two-minute staleness window, long enough that a
   live request is never interrupted.
3. **A confirmed row with no server id** was skipped in silence. It now says so.

**The confirm request also had no timeout at all**, unlike every other network
call in the client. A connection that never settled meant the `catch` never
ran, so the row could not even be marked failed. It is now bounded at 20
seconds — and an aborted request counts as retryable, not as a verdict, or the
timeout itself would have marked receipts permanently failed.

Two related corrections to the retry policy:

- A confirm is now abandoned only for a verdict the server will repeat forever.
  Transport failures retry indefinitely against a capped backoff, because until
  the server has the receipt it exists on one device.
- A permanently failing row no longer blocks every row behind it. The old code
  broke out of the loop on any error.
- Retry counters reset at the extract/confirm boundary. One pair of columns
  serves both queues, so a scan that needed three extract retries used to start
  its confirm backoff three deep and burn three of its five attempts.

**Verified end to end against staging on a device.** An edited merchant now
reaches the database. Separately, a receipt that had been stranded mid-sync for
half an hour recovered and pushed its edit **on its own** once the reclaim
shipped, without a rescan — which confirms the diagnosis rather than just the
fix.

## 4. Smaller user-facing changes

- **Offline captures now say so.** A capture queued because the device is
  offline shows a dialog explaining the receipt is saved and will be processed
  on reconnect; repeats within a minute drop to a toast so scanning a stack of
  receipts offline does not mean dismissing a dialog each time. This covers
  Precise too, which previously showed nothing at all. Late outcomes arriving
  after Precise's "being processed" dialog get a toast, never a second dialog.
- **The receipt list shows real text.** It was rendering the raw status enum —
  a queued scan read "llm failed retryable" to the user, in release builds too.
  Every status now maps to human copy through an exhaustive record, so a new
  status cannot be added without giving it one. "Waiting to retry" rather than
  "Waiting for network", because those states also cover a slow or 5xx server.
- **The list refreshes while the queue drains** — on reconnect, on foreground,
  and on a short poll while any row is still in flight. It previously loaded
  once and never again, so a receipt queued offline sat on "Processing receipt"
  until the view was reopened. A failed refresh no longer blanks the list.

## 5. Not done — open items

Carried forward from 31 July, unchanged: **4.2** (a rejected scan still deletes
the user's photo silently — now the most serious open item), **4.4** (category
lookup timing; measure first), **4.5** (image-durability contract, with two B3
assertions deliberately left failing), and the process items in **4.6**.

Note 4.3 is partly addressed: the offline case now has proper messaging in both
modes. The agreed Precise "this may take a while" up-front dialog, and removing
the interim spinner, are still not built.

New from this session:

### 5.1 Hydrate on fresh install — agreed, unblocked, not started

This was the task in progress when the confirm bug stopped it. It is now safe
to build.

Decision taken: **single device**. If a user signs in elsewhere they should be
told, which makes the down-sync a one-shot hydrate rather than continuous
sync — no cursor, no tombstone window, no conflict resolution, because the
local database is empty when it runs.

Three wrinkles found while planning it:

- `receipts.image_uri` is `NOT NULL` locally, but a hydrated row has no local
  file. Make it nullable and fetch the image lazily when a receipt is opened.
- Local rows store a `fields` JSON blob; the server stores columns. Hydrate has
  to rebuild the local shape, including mapping `category_id` back to a name.
- Identity is already solved — `receipts.capture_id` is the device-generated id
  and is unique, so hydrated rows land with the key they had before.

Write it as an idempotent upsert over pages, not a blind insert, and store a
cursor from day one. Then a delta pull later is the same function with a
`since` argument.

### 5.2 Single-device enforcement

Make it **takeover, not a hard block** — "you're signed in on another device,
continue here?". A hard block means a lost or broken phone locks the user out
of their own data permanently. Build `user_devices` (user_id, device_id,
last_seen_at, is_active) rather than a column on `profiles`: same effort now,
and relaxing to multi-device later becomes a policy change rather than a
migration. It must be enforced in the edge functions; a client-side check is
decoration.

### 5.3 Multi-device later — the schema is ready, keep it that way

The expensive decisions are already correct: client-generated stable ids,
`deleted_at` tombstones, `updated_at` maintained by trigger, RLS scoping. What
would be needed later is additive: timestamps on `receipt_items` (item edits
currently do not touch the parent's `updated_at`, so they would be invisible to
a delta pull), a `pull_changes` RPC, a local cursor, and a tombstone retention
policy.

Two rules to avoid closing that door: **never hard-delete a receipt** — always
set `deleted_at` — and never let the client write `updated_at`.

### 5.4 Line-item sync

Items are flattened to plain text before reaching the device, so item edits
cannot be pushed. Closing this means carrying structured line items through the
extract contract (pinned to HANDOFF §5 and covered by the gates) and turning
the item editor from a text area into rows with quantity and amount. Do it when
editing from Search is wired, since that is when item editing becomes a real
workflow. It needs a decision-log entry.

### 5.5 Delete receipts — designed, deliberately paused

Agreed shape: hard-delete rows the server has never seen (nothing to
reconcile), soft-delete synced ones and push the tombstone, purge locally after
the server acks. Swipe one direction only, with undo rather than a confirmation
dialog. **No scan refund** — and note that nothing is deducted until the server
answers, so a capture queued offline and deleted before it sends never cost a
scan in the first place.

### 5.6 A terminal sync failure is still invisible

`sync_failed_final` is now rare, but such a row keeps `status =
'confirmed_local'` and has fields, so the list renders it as a normal saved
receipt. The user is told their receipt is safe when the server never got it.
Surfacing it needs a badge in the list rather than a status label.

### 5.7 Release builds silently target production

`--configuration Release` sets `NODE_ENV=production`, so Expo loads
`.env.production` — which points at the **production** Supabase project, not
staging. A local release build therefore talks to prod (currently paused) and,
because the session is keyed by project ref, cannot even see the staging
session. It was worked around for one build by pinning the staging values in
the build environment. The real fix is an explicit env for the `preview` EAS
profile, or renaming that file so a local release build cannot pick it up.

### 5.8 Smaller

- **23 orphaned images on staging.** The receipts table was cleared at the end
  of the session (24 rows, 109 line items) but the images were not: the CLI's
  `storage rm` reports success and deletes nothing, and retrieving a
  service-role key was blocked. Delete the `a77b2837…` folder in the dashboard.
  `scan_ledger` was deliberately left alone, so the test account's quota is
  unchanged.
- **`expo-updates` is configured on release builds.** Worth confirming which
  channel a local release build resolves to; an OTA bundle could serve JS that
  neither the build nor the branch matches.
- **The simulator can never show the camera.** `useCameraDevice('back')`
  returns null there, and that branch renders the same spinner as the transient
  "still enumerating" case, so it reads as a hang. A short timeout falling back
  to "No camera available" would make it self-explanatory.
- **Editing a saved receipt from Search is not wired yet.** When it is, it
  should reuse the confirm save path rather than adding an endpoint.

## 6. Notes for whoever picks this up

**Gate changes, stated deliberately.** Six new backend assertions cover the
confirm write and the shared category rule. Two existing assertions were
repointed from `extract-balanced` to the shared module, and one was rewritten
because it asserted the old status-only write. The most important new one was
negative-tested: restoring the old write made the gate fail with "confirm
writes the field patch, not just a status", then it was restored.

`b4:app`, `b4:backend`, typecheck and lint all pass. `b3:app` still fails its
image-durability assertion, unchanged and pre-existing — see 4.5.

**Operational rule, unchanged and now wider:** shared code is copied into each
function at deploy time. `_shared/categories.ts` is used by both
`receipt-confirm` and `extract-balanced`, so a change to it means redeploying
both, exactly as with `_shared/quota.ts`.

**Three claims in the codebase turned out to be false, and each cost time.**
Worth treating source comments and prior handovers as hypotheses:

1. A comment said a failed extract leaves the row in `pending_extract`; the
   code sets `llm_failed_retryable`. That led to telling the tester queued
   receipts do not appear in Search, when they do.
2. The 31 July handover says the scan balance is decremented locally when
   offline. It is not — nothing is deducted until the server answers. That
   changes the answer to whether deleting an unsent capture should refund a
   scan: there is nothing to refund.
3. A diagnosis of "confirm has never worked" was drawn from the five most
   recent rows; seven older receipts had confirmed fine. Count before
   concluding.

**The device's local database can be read on the simulator** (via the app
container's `Documents/SQLite/parse.db`) but not on a physical device. Most of
the debugging in this session was inference from the staging database plus the
code, and the one thing that settled it was putting a dev build on the phone
with Metro attached so the client could speak. Do that first next time.
