Supplements `docs/B4-handover-2026-07-31.md`, which still describes the B4
architecture correctly. This covers a session that began with open item 4.1

## 1. The app can cold-start without a network (4.1, closed)

**The problem.** Start-up ran one network transaction that had to succeed before
the session was applied, so launching offline discarded a valid stored session
and dropped the user on sign-in. The B3 offline capture queue was unreachable in
exactly the situation it exists for.

**What changed.** Auth state is three-valued — restoring, authenticated, signed
out — and restored from local storage first, with reference data revalidated in
the background where failing changes nothing visible. `signed_out` is reachable
only from an empty token store or an explicit sign-out, never from a failed
request.

The app keeps its own record of who is signed in (`auth_cache`), separate from
the tokens, because an access token older than an hour cannot be refreshed
offline: Supabase answers "no session" while deliberately leaving the tokens on
disk. Without a local record of the identity, that is indistinguishable from
having no account. Routing switched from `session` to an `authenticated` flag.

Fixed in passing: Supabase auto-refresh was never wired to `AppState` (React
Native has no page lifecycle for it, so the token was only refreshed lazily at
the moment of use — which is how it got old enough to be unrefreshable); a
token refresh no longer flashes a full-screen spinner every 50 minutes; and
signing out now clears locally even if the server call fails.

**Not covered:** the branch where identity comes from the snapshot alone. In
testing the access token was still valid. To exercise it, leave the app closed
for over an hour, then launch offline.

## 2. The user's edits never reached the database

**The problem.** Confirming a receipt sent the corrected fields to the server
and the endpoint read nothing but the receipt id. Every edit — merchant, date,
total, category, notes — lived only on the device while the database kept the
model's original reading. Nothing surfaced it because the app never read
receipts back.

This was found while planning the restore, and is why that work stopped:
restoring from a server holding the model's guesses would silently revert every
correction, which is worse than an empty list because wrong numbers read as
correct.

**What changed.** Confirmation writes merchant, date, total, currency, category
and notes, and is written as "save these values", safe to call repeatedly — so
wiring editing from the Search screen later reuses it rather than adding a
second endpoint.

Resolving a category name to an id, and refusing any category the account has
not selected, moved into `functions/_shared/categories.ts`, used by both
extraction and confirmation. Writing that rule twice is precisely how Balanced
drifted from Precise. The cache and timing instrumentation moved with it, so
the 4.4 latency investigation is unaffected.

**Line items are deliberately not written.** The model captures name, quantity
and amount, but that structure is flattened to plain text before it reaches the
device, so the phone cannot push back what it never received. Writing the
strings would overwrite real quantities with placeholders. See §8.4.

## 3. Rows that nothing ever re-drove

Three states could leave a receipt sitting "saved" on the phone forever while
the server never heard about it. All invisible: no error, no retry, and the
receipt looked fine in the app.

1. **`sync_failed_final`** — after five failed attempts a confirmed receipt was
   marked terminally failed, and the work list never selects that state.
2. **`syncing` / `uploading`** — both queues mark a row in-flight *before* the
   network call, and neither work list selects those states. A request that did
   not survive the process stranded the row permanently. Both are now reclaimed
   after a two-minute staleness window.
3. **A confirmed row with no server id** was skipped in silence. It now says so.

**The confirm request also had no timeout**, unlike every other network call in
the client, so a connection that never settled meant the `catch` never ran and
the row could not even be marked failed. Now bounded at 20 seconds — and an
abort counts as retryable, or the timeout itself would have marked receipts
permanently failed.

Retry policy corrections: a confirm is abandoned only for a verdict the server
will repeat forever, transport failures retry indefinitely against a capped
backoff, a permanently failing row no longer blocks every row behind it, and
retry counters reset at the extract/confirm boundary (one pair of columns
serves both queues).

**How this was proven.** A receipt stranded mid-sync for half an hour recovered
and pushed its edit **on its own** once the reclaim shipped, with no rescan —
which confirms the diagnosis, not just the fix.

## 4. The local copy is now kept in step with the server

The largest piece, and a scope change agreed mid-session.

**Why.** The local database is what every offline decision reads — the shutter
gate, duplicate detection, totals. It is only as trustworthy as its agreement
with the server, and nothing maintained that agreement; it rested on "the
device is the only writer". That is already scheduled to stop being true:
`RETENTION_FINANCIAL_YEARS` implies a purge that deletes rows nobody on the
device asked to delete, and `account_tombstones` the same. The app would have
gone on showing, exporting and totalling receipts the server had destroyed.

**What it does.** A cursor-based pull (`src/lib/receipts/server-sync.ts`) on
launch, on reconnect, and on foreground when the last pass is over five minutes
old:

- A cursor of the newest `updated_at` seen. The first pass has no cursor and
  takes everything — so a reinstall and steady-state sync are one code path.
- Fetches `>=` the cursor, not `>`, so rows sharing a timestamp cannot fall
  through the gap; re-applying a row is idempotent.
- **Soft-deleted rows come back too and become local deletions**, image
  included. A pull that only inserts is not a mirror; it can never let go.
- The cursor advances only over rows actually applied, so an interrupted pass
  resumes rather than skips.

**The conflict rule is deliberately blunt: un-acked local work always wins.** A
row is overwritten only when fully settled (`status = 'synced'` and
`result_sync_status = 'synced'`). Anything mid-flight, awaiting review, or
confirmed-but-not-yet-pushed is left alone, because the device is the only
place that version exists. A tombstone for a row with unsent work is **skipped
rather than obeyed** — pushing it will fail against a deleted receipt and
surface then, which beats destroying something unrecoverable.

**Scope, stated plainly.** This is the *down* direction only; local→server
remains the outbox, driven on camera mount and reconnect. It covers `receipts`
and their line items — not profile, categories, quota or subscriptions, which
have their own refreshes — and not image *files*, only the storage path.

**Verified against staging**, changing data on the server and watching the
device follow: a soft delete removed the row locally, an edit propagated,
un-deleting re-added it, the cursor advanced throughout, and untouched rows
were never refetched.

## 5. One account could see another's receipts

Local rows carry no user id — the device always assumed a single account — and
signing out leaves them in place. So signing in as someone else showed the
previous user's receipts, and once the pull existed it was worse: the incoming
user would see the wrong receipts *and* never get their own, because the first
pass only ran against an empty database.

A `local_owner` marker records whose receipts these are. When a different
account signs in, the store and its image files are dropped and that account
syncs clean.

**Deliberately not triggered by sign-out.** A user signing back into their own
account would lose any capture that had not reached the server. Sign-in as a
different user is the only moment the leak matters. An unknown owner is treated
as "adopt", not "foreign", so existing installs keep their receipts — verified
on a device holding three receipts and no owner record.

## 6. Smaller user-facing changes

- **Offline captures now say so.** A capture queued because the device is
  offline gets a dialog explaining the receipt is saved and will be processed
  on reconnect; repeats within a minute drop to a toast. This covers Precise
  too, which previously showed nothing at all. Late outcomes arriving after
  Precise's "being processed" dialog get a toast, never a second dialog.
- **The receipt list shows real text.** It rendered the raw status enum — a
  queued scan read "llm failed retryable" to the user, in release builds too.
  Every status now maps to copy through an exhaustive record, so a new status
  cannot be added without giving it one. "Waiting to retry" rather than
  "Waiting for network", since those states also cover a slow or 5xx server.
- **The list refreshes while the queue drains** — on reconnect, on foreground,
  and on a short poll while any row is in flight. It previously loaded once, so
  a receipt queued offline sat on "Processing receipt" until the view reopened.
  A failed refresh no longer blanks the list.

## 7. Verification status

**Proven end to end against staging:** the offline cold start; the confirm
endpoint persisting an edited merchant; a stranded row recovering by itself;
the first full pull onto an empty device (3 receipts, edits intact, categories
resolved, items rebuilt, identity preserved on `capture_id`); server-side
delete, edit and un-delete all reflected on the device; and an existing install
keeping its receipts when the owner marker was introduced.

**All of that was on the simulator**, against the real staging backend, except
the confirm fix which was proven on the physical device. The sync is pure JS
with no native surface, so device behaviour should be identical — but see 8.1.

**Gates:** `b4:app`, `b4:backend`, typecheck and lint pass. `b3:app` still fails
its image-durability assertion, unchanged and pre-existing (4.5).

Gate changes were deliberate: six new backend assertions cover the confirm
write and the shared category rule; two existing ones were repointed from
`extract-balanced` to the shared module; one was rewritten because it asserted
the old status-only write. The most important was negative-tested — restoring
the old write made the gate fail, then it was restored.

## 8. Open items

Carried forward unchanged: **4.2** (a rejected scan still deletes the user's
photo silently — now the most serious open item), **4.4** (category lookup
timing; measure first), **4.5** (image-durability contract, two B3 assertions
deliberately failing), and the process items in **4.6**. 4.3 is partly done —
the offline case now has proper messaging in both modes; the Precise up-front
dialog and removing the interim spinner are not built.

### 8.1 The device needs rebuilding, and holds stale rows

The phone runs a build from before all of this. More importantly: **staging was
cleared with a hard `DELETE`**, so ~24 receipts the phone still holds no longer
exist server-side — and hard deletes leave no tombstone, so the sync can never
remove them. Delete and reinstall the app on the device so it starts empty and
pulls the three real receipts.

### 8.2 Never hard-delete a receipt again

The mirror only works for soft deletes. Anything that issues a real `DELETE`
against `receipts` strands those rows on every device forever. This applies to
maintenance and to any future delete feature — always set `deleted_at`.

### 8.3 Single-device enforcement

Agreed but not built. Make it **takeover, not a hard block** — "you're signed in
on another device, continue here?" — because a hard block locks a user out of
their own data when a phone is lost or broken. Build `user_devices` (user_id,
device_id, last_seen_at, is_active) rather than a column on `profiles`: same
effort now, and relaxing to multi-device later becomes a policy change rather
than a migration. It must be enforced in the edge functions.

### 8.4 Line-item sync

Items are flattened to plain text before reaching the device, so item edits
cannot be pushed. Closing it means carrying structured line items through the
extract contract (pinned to HANDOFF §5, covered by the gates) and turning the
item editor into rows with quantity and amount. Do it when editing from Search
is wired. Needs a decision-log entry.

### 8.5 Delete receipts — designed, paused

Hard-delete rows the server has never seen, soft-delete synced ones and push
the tombstone, purge locally after the ack. Swipe one direction only, with undo
rather than a confirmation dialog. **No scan refund** — and note nothing is
deducted until the server answers, so a capture queued offline and deleted
before it sends never cost a scan.

### 8.6 A terminal sync failure is still invisible

`sync_failed_final` is now rare, but such a row keeps `status =
'confirmed_local'` and has fields, so the list renders it as a normal saved
receipt — the user is told their receipt is safe when the server never got it.
Needs a badge in the list rather than a status label.

### 8.7 Release builds silently target production

`--configuration Release` sets `NODE_ENV=production`, so Expo loads
`.env.production`, which points at the **production** project (currently
paused). Because the session is keyed by project ref, such a build cannot even
see the staging session. Worked around once by pinning staging values into the
build environment. Real fix: an explicit env for the `preview` EAS profile, or
rename that file.

### 8.8 Multi-device later — keep the door open

The expensive decisions are already right: client-generated stable ids,
`deleted_at`, `updated_at` by trigger, RLS scoping, and now a cursor. What is
still needed is additive: timestamps on `receipt_items` (item edits do not touch
the parent's `updated_at`, so they would be invisible to the delta), a
tombstone retention policy with a "cursor too old, full resync" signal, and
per-row conflict handling if two devices ever write.

### 8.9 Smaller

- **23 orphaned images on staging.** The CLI's `storage rm` reports success and
  deletes nothing, and retrieving a service-role key was blocked. Delete the
  `a77b2837…` folder in the dashboard. `scan_ledger` was left alone, so the
  test account's quota is unchanged.
- **`expo-updates` is configured on release builds.** Worth confirming which
  channel a local release build resolves to; an OTA bundle could serve JS that
  matches neither the build nor the branch.
- **The simulator can never show the camera.** `useCameraDevice('back')`
  returns null there and that branch renders the same spinner as the transient
  "still enumerating" case, so it reads as a hang. A short timeout falling back
  to "No camera available" would make it self-explanatory.
- **Editing a saved receipt from Search is not wired.** When it is, reuse the
  confirm save path rather than adding an endpoint.

## 9. Notes for whoever picks this up

**Operational rule, now wider:** shared code is copied into each function at
deploy time. `_shared/categories.ts` is used by both `receipt-confirm` and
`extract-balanced`, so changing it means redeploying both — as with
`_shared/quota.ts`.

**A five-minute staleness guard governs revalidation.** A quick relaunch may
legitimately do nothing; this looked like a failure during testing and was not.
Use `xcrun simctl terminate` then `launch` to force a genuine cold start.

**Four claims in the codebase or its documents turned out to be false**, and
each cost real time. Treat comments and prior handovers as hypotheses:

1. A comment said a failed extract leaves the row in `pending_extract`; the code
   sets `llm_failed_retryable`. That produced a wrong answer to the tester about
   whether queued receipts appear in Search.
2. The 31 July handover says the scan balance is decremented locally when
   offline. It is not — nothing is deducted until the server answers. That
   changes whether deleting an unsent capture should refund a scan: there is
   nothing to refund.
3. A diagnosis of "confirm has never worked" was drawn from the five most
   recent rows; seven older receipts had confirmed fine. Count before
   concluding.
4. `supabase storage rm` reports `{"deleted":[]}` and exits successfully while
   removing nothing. Verify storage deletions by listing afterwards.

**The device's local database can be read on the simulator** (app container →
`Documents/SQLite/parse.db`) but not on a physical device. Most of this
session's debugging was inference from the staging database plus the code, and
what finally settled it was putting a dev build on the phone with Metro
attached so the client could speak. Do that first next time.

**Reading staging directly is worth setting up.** `SUPABASE_DB_URL` in `.env` is
a direct Postgres connection; a throwaway `pg` client answered questions in
seconds that had taken an hour of inference. The CLI has no `functions logs`
subcommand in 2.109.1.
