# B4 Handover — 31 July 2026

Supplements `docs/B4-handover.md` (30 July). That document still describes the
overall B4 architecture correctly; this one records a day of work on the Balanced
extraction path, the quota system, and gate coverage — plus a set of issues found
along the way that are not yet fixed.

Branch: `feat/b4-extraction-fast-path`
Staging project: `receiptflow-staging` (`wfboznibkhsfxteejxco`)
All work below is **uncommitted** at time of writing. Edge functions **are**
deployed to staging.

---

## 1. Context: why this session happened

A review of the Balanced path found that it had drifted from the Precise path in
ways nobody had noticed, because the automated gate only ever inspected Precise.
Balanced is the default mode — the one nearly every scan uses — so several
significant defects were live and invisible.

The theme running through everything below: **the same rule existing in two
places will diverge, and a gate that watches the wrong file will tell you
everything is fine while it happens.**

---

## 2. What was fixed

### 2.1 Categories were hardcoded (Balanced only)

**The problem.** Balanced offered the model a hardcoded list of all ten
categories rather than the user's own selections, and then wrote every single
receipt to the database as "Miscellaneous" regardless of what the model decided.
The app displayed the correct category because it kept its own copy locally, so
the fault was invisible in the UI. It would have surfaced later as wrong
category filters, wrong export totals, and wrong data on any second device.

**What changed.** Balanced now reads the user's actual selected categories,
offers only those to the model, and stores the real category id. The list is
cached briefly per server instance, and the camera's existing warm-up call primes
that cache before the shutter is pressed. If the category lookup fails, it falls
back to the standard list rather than failing the scan.

**Verified on staging:** a coffee-shop receipt now stores "Meals &
Entertainment" instead of "Miscellaneous".

### 2.2 The receipt id could refer to a row that never existed

**The problem.** Balanced generated a receipt id, returned it to the app
immediately, and only then wrote the database row in a background task. If the
server instance died mid-write, the app held an id for a receipt that was never
created — and every later attempt to confirm it would fail forever. Separately,
a redelivered capture would try to overwrite an existing row's primary key while
its line items still pointed at the old one.

**What changed.** The receipt row is now claimed in the database at the same
moment the model call starts, so the two overlap and cost no extra time. The id
returned to the app always exists. A repeated delivery of the same capture reuses
the existing row instead of creating a second one, and the background write is
guarded so a late duplicate cannot overwrite a receipt the user has already
confirmed, nor charge a second scan.

Two further bugs were fixed in passing: the background write no longer wipes the
image path that the separate image-backup upload sets (a genuine race), and a
failure to claim the row now returns a retryable response so the capture stays
queued rather than being lost.

### 2.3 Quota was not enforced at all in Balanced

**The problem.** Precise checked the user's remaining scans and refused when
exhausted. Balanced did not check at all — it scanned, then recorded the usage
afterwards in the background. Since Balanced is the default mode, the free tier
was effectively unenforced and every over-quota scan still cost model spend.

**What changed.** The counting rule now lives in exactly one place, in the shared
contracts package, and is used by the Precise function, the Balanced function and
the app. Neither side can drift again — the gate now fails if the app or either
function re-declares the cap or the product identifiers.

The paywall routing was also corrected: a paying user who hits the monthly cap is
now pointed at the higher tier rather than the entry tier.

### 2.4 A client-side gate so the user is stopped before the work

Previously the only quota check was on the server, so an out-of-scans user still
took a photo, waited, and uploaded before being told no.

The app now keeps a local copy of the remaining balance and checks it the instant
the shutter (or the gallery button) is tapped. No photo, no upload, no model call.

Design points worth knowing:

- The local copy is **advisory only**. The server still checks every scan and
  remains the sole authority. Tampering with the local value achieves nothing.
- It is stored in the ordinary local database, deliberately not encrypted — it is
  not a secret.
- Both extract functions now return the remaining balance in their response, so
  the local copy refreshes off a call the app already makes. No polling, no extra
  endpoint. It also refreshes when the camera opens and when the app returns to
  the foreground.
- Offline with a known balance behaves correctly: the number is used and
  decremented locally, so all remaining scans work without connectivity.
- **When the balance has never been synced at all** (fresh install, cleared data)
  the scan is allowed optimistically. Blocking would tell someone with a poor
  connection they are out of scans when they are not, and the server still
  refuses if they genuinely are. This was an explicit product decision.

### 2.5 Out-of-scans is now a proper message, not a silent failure

Previously the app treated a quota rejection exactly like a dropped connection:
it queued the capture and retried it several times, showing nothing meaningful to
the user (and, in a development build, a raw internal error string).

Now it is treated as a verdict rather than a failure — no retrying, since
retrying can never succeed — and the user gets a proper dialog explaining they
are out of scans, with **OK** and **Upgrade**. Upgrade opens the Subscription
tab.

**Important caveat:** the Subscribe button on that screen is still a non-working
visual shell. Real billing is a later phase. The user is routed to the right
place but cannot yet pay.

### 2.6 Precise no longer shows contradictory alerts

Precise announced "Receipt is being processed" as soon as the on-device
pre-check passed — before the server had said anything. So a rejection produced
two stacked dialogs: a promise, immediately contradicted.

The app now shows a neutral progress indicator while it waits, and only promises
background completion once the server has genuinely gone quiet past the visible
deadline. This fixed the same contradiction for every rejection type, not just
quota.

Note this is an interim state — see open item 4.3.

### 2.7 The retry queue was discarding late results

Found while investigating a stuck row during testing, and probably the most
serious defect of the day.

When a queued capture was retried and the server took longer than the visible
deadline to answer, the app rescheduled the row and **threw the eventual answer
away**. If that answer was a rejection, it was never applied. Worse, if it was a
**success**, the server had persisted a real receipt while the app left its row
stuck displaying "Processing receipt" forever — and would later scan it again as
if nothing had happened.

Late results are now applied properly.

### 2.8 Quota rejections were slower than they should have been

The Balanced function was waiting for the category lookup before deciding on
quota, even though quota needs nothing from it. On a cold server instance that
lookup took up to a second and a half, which could push a rejection past the
point where the app had stopped listening — directly triggering 2.7.

Quota is now settled first and returns in a few hundred milliseconds.

### 2.9 Gate coverage

The B4 backend check only ever read the Precise function. It has been extended to
cover the Balanced path and the shared quota rule, and the app-side check now
covers the client gate. Roughly twenty-five new assertions in total.

These were **negative-tested**: the code was deliberately reverted to its broken
state (hardcoded category, bypassed quota gate, invented receipt id, client
re-implementing the cap) and each one confirmed to fail the gate, then restored
byte-for-byte.

Four assertions in the **B3** gate were also found to be silently broken by
earlier B4 work — a renamed variable, a changed function signature, a form-field
access style, and a fixture literal that had become real logic. All were stale
checks rather than real regressions, and were repaired. One was loosened
deliberately: B3 pinned the image size to an exact value, and B4 had legitimately
tuned it downward, so it now asserts the specification's ceiling instead. Revert
that if you would rather it pin an exact number.

## 3. Deployment and current state

Both edge functions are deployed to staging and confirmed to start correctly.

**Operational rule, important:** the quota logic is shared by both functions but
is copied into each one at deploy time. If you change it, you **must redeploy
both functions**, or one will silently keep running the old rule — recreating
exactly the drift this work removed.

A related constraint: the shared rule file must stay free of imports, because the
server runtime cannot resolve the import style the rest of the contracts package
uses.

The test account's balance has been restored to 443 and the temporary test flag
used during testing has been removed. Devices may still hold a stale cached
balance until the app is reopened.

## 4. Not done — open items

Ordered roughly by how much they matter.

### 4.1 The app cannot cold-start without a network

**Found during testing, not yet fixed. Arguably the most serious item here.**

If the app is fully closed and reopened with no connectivity, the user is sent
back to the sign-in screen. Their session is valid and stored the whole time — it
simply never gets applied, because the start-up sequence tries to load reference
data from the server first and gives up entirely when that fails.

This undermines the offline capture queue built in B3: that queue exists so scans
survive without connectivity, but a user who reopens the app in a basement cannot
reach the camera to make one.

To reproduce: fully quit the app, enable Airplane Mode, launch it. Expect a few
seconds of loading, then the sign-in screen.

The fix in principle is to restore the stored session first and treat the
reference-data load as a separate step that is allowed to fail. It is a real
change to the start-up flow and should be done deliberately.

### 4.2 A rejected scan still destroys the user's photo

When the server refuses a scan for quota, the app deletes the capture and its
photo with no message.

This was defensible when it could not happen without the user watching. It no
longer is: optimistic offline scanning is now deliberately allowed, so a user can
photograph a receipt offline, have it queued, and have it quietly destroyed when
connectivity returns — with nothing shown at any point.

Standard practice is to keep the capture in a visible blocked state with an
upgrade action, and not to retry it automatically. Roughly half a day: a new
status, the list rendering, two actions, and a rule to purge abandoned ones after
about thirty days. Genuine rejections such as "not a receipt" should keep
deleting, since the user is told about those.

### 4.3 Precise progress messaging — agreed design not yet built

The agreed end state, now that the client gate exists:

- Out of scans → immediate dialog, no photo taken, in both modes (**done**)
- Balanced with balance → placeholder card filling in with results (**already
  the behaviour**)
- Precise with balance → an up-front "this may take a while" dialog dismissed
  with OK, and **no** spinner
- Any late failure after that dialog → a non-blocking toast, never a second
  dialog

Only the third and fourth points remain. About thirty minutes. The current
spinner is scaffolding that should be removed in the same change.

### 4.4 The category lookup may be costing real time

Server logs showed the category read taking between 243 and 1542 milliseconds,
and every warm-up call landing on a brand-new server instance — meaning the cache
added for it rarely helps. It no longer blocks the quota decision, but it still
sits in front of the model call.

**Measure before acting:** check the category timing figures on the next few
successful Balanced scans. If real scans land on warm instances, the cache is
working and this matters much less than the warm-up logs suggest.

If it is real, the fix is for the app to send its category list with the request
— it already has it — and for the server to resolve the authoritative category
during the background write, where timing does not matter. That removes the
round trip from the critical path without weakening the validation rule. Two to
three hours.

### 4.5 The image-durability contract is still unresolved

Carried over from the start of the session. Balanced returns a storage path for
an image that has not been uploaded yet; the upload follows separately. No
captures are being lost today, because the app keeps its local copy until the
upload is confirmed. The two exposures are that a permanently failed upload
leaves a receipt with no image and nothing knows, and anything trusting that path
early gets a dead link.

Two B3 gate assertions are **deliberately left failing** against this. They are
not stale — they are correctly objecting that the rule changed without being
rewritten. They should go green as part of resolving this, not before. Do not
"fix" them by rewriting the assertions.

The original rule was written for a photo-first design and does not fit a
text-first mode; expect to redefine it rather than restore it.

### 4.6 Smaller items

- **Camera capture failures.** Five hardware-level capture errors appeared in
  device logs, currently swallowed into a warning. Cause unknown — possibly rapid
  shutter taps. Worth a look.
- **Debug text visible during development.** Raw internal error strings appear
  under the processing overlay in development builds only. This is intentional
  and invisible in a release build, but it is confusing during testing and was
  twice mistaken for a crash.
- **A stuck row from testing.** One capture is sitting as "Processing receipt" on
  the test device. It is either the offline test capture or a leftover from an
  earlier run — this could not be determined without reading the device's local
  database. Reopening the app should now resolve it either way, thanks to 2.7.
- **Phase tracking is stale.** The phase-state file still reports B1 in progress,
  and the CI job meant to enforce phase ordering was never built. A process
  decision, not a code one.
- **No decision-log entry for the Balanced/Precise split.** The playbook requires
  one for anything not in the original documents. Worth writing before B5, mainly
  so B5's tests get rewritten deliberately rather than discovered as failures.
- **B5 needs a decision.** All five of its planned tests assume the original
  delayed-response, circuit-breaker and sweeper design. The app now uses a
  client-side visible-deadline approach instead. Decide whether B5 builds the
  original design, formalises the current one, or both.

## 5. Notes for whoever picks this up

**Verification status.** Everything above is source-checked and passes the
automated gates. The category fix, the quota rejection, the ledger behaviour and
the reservation cleanup were confirmed against the staging database on a real
device. The reordered quota decision and the late-result fix are deployed but
**not yet retested on a device**.

**Two corrections made during the session**, worth recording because they show
where the reasoning went wrong. Both came from reading logs and inferring rather
than checking state:

1. A capture was reported as silently deleted; the tester checked the app and it
   was still there. That correction led directly to finding the discarded
   late-results bug in 2.7 — the more serious defect.
2. The same event was described as happening "on reconnect" when the network had
   in fact returned by itself seconds earlier.

The lesson worth carrying: the device's local database cannot be inspected from
the development machine, so any claim about local rows is inference. Say so, or
check.
